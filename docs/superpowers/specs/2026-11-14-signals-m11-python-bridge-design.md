# M11 «Мост в Python» — проект

Строка M11 из `03-design.md` §13: выгрузка сигналов, коэффициентов и отчётов в `.npy`/`.npz` и обратная загрузка; генерация скрипта на pywt/scipy по графу `.sig`, дающего те же числа. Критерий из таблицы: скрипт по каждому примеру `.sig` совпадает с программой до 10⁻¹².

Решения пользователя:

- скрипт нужен **и чтобы читать и учиться по нему, и чтобы сверять числа**;
- подход **А**: один самодостаточный файл; вызовы pywt/scipy там, где они дают те же числа, свои функции на numpy для остальных блоков, только нужных этому графу;
- скрипт строится для **всех 136 блоков**; неподдержанный блок останавливает выгрузку и называется;
- **предпросмотр в VS Code (С37)** входит в этот этап последним PR перед выпуском;
- **точность против читаемости — вариант «а»**: где функция scipy или pywt даёт те же числа только до 10⁻⁸…10⁻¹⁰, скрипт всё равно вызывает её, а допуск блока записан в этом документе (§5.1) и печатается в таблице сверки вместе с блоком, который его задал. Исключение — вейвлеты: если фильтры pywt не совпадают с фильтрами Signals до последнего разряда, скрипт строит `pywt.Wavelet(..., filter_bank=…)` из чисел Signals одной строкой, и вейвлет-графы остаются на 10⁻¹²;
- **знак детальных коэффициентов — вариант «а»**: вне Signals всё в знаке pywt. При записи `.npz` знак деталей меняется на знак pywt, при чтении — обратно на знак Signals; в файле есть ключ `detail_sign`, в заголовке скрипта — строка об этом;
- после M11 — выпуск **0.9.0**.

Остальные решения ниже — мои, они перечислены в конце.

## Цели

1. Любое значение конвейера (сигнал, коэффициенты, отчёт) и банк фильтров любого вейвлета выгружаются в `.npy` или `.npz`, которые `np.load(..., allow_pickle=False)` читает без потерь.
2. Сигнал и коэффициенты загружаются обратно из `.npy`/`.npz`, записанных Signals или самим numpy/pywt.
3. `signals python graph.sig` пишет скрипт `.py` или тетрадь `.ipynb` и рядом файл данных `.npz`. Скрипт зависит только от numpy, scipy и PyWavelets, повторяет граф узел за узлом и в конце сверяет каждый щуп и каждый отчёт с программой.
4. Сверка проходит для каждого примера `.sig` и для каждого из 136 блоков: до 10⁻¹², а у блоков из таблицы допусков (§5.1) — до их записанного допуска. Это проверяется в CI.
5. Скрипт читается: где у блока есть функция pywt или scipy, дающая те же числа, вызывается она; свои функции короткие, названы по блоку и написаны так, чтобы по ним можно было учиться.
6. `signals explain` показывает, как блок записывается на Python, и получает `--json` (Н69).
7. Расширение VS Code показывает рядом с `.sig` живой предпросмотр: отчёт, графики щупов, ошибки с переходом к строке (С37).

## Не цели

- Модуль `import signals` и любые привязки ядра к Python — это не-цель проекта (`03-design.md` §2). Мост — только файлы и сгенерированный текст.
- Серии прогонов (`signals sweep`) и подграфы в скрипте. `--set` поддерживается, как в `run`.
- Повторение в Python ошибок программы. Если граф в Signals не выполняется, выгрузка сообщает ту же ошибку и ничего не пишет.
- Генератор случайных чисел программы на numpy. `std::normal_distribution` стандарт не фиксирует, поэтому случайные отсчёты всегда берутся из `.npz`.
- Чтение FLAC и MP3 в Python: их отсчёты приходят из `.npz`.
- Загрузка банков фильтров из `.npz` (для них есть `.flt` и «Мои фильтры»). Выгрузка банка в `.npz` — есть.
- Задания учебного пути, проверяющие Python-код.
- Переписывание на numpy алгоритмов, для которых есть вызов scipy или pywt, только ради 10⁻¹² (`remez`, проектирование БИХ и т. п.): по решению пользователя у них остаётся библиотечный вызов и записанный допуск.
- Совпадение блоков с выбором (§5.2) на точном равенстве решающих величин.
- Публикация расширения VS Code в Marketplace.

## Анти-цели (провал, даже если всё работает)

- Скрипт, который «почти совпал»: допуск ослаблен без записи в этом документе или сверка тихо пропускает щуп или поле отчёта.
- Узел, молча выпавший из скрипта, или блок, у которого Python-версия считает не то же, что программа, а сверка этого не видит (например, потому что значение подгружено из `.npz`, хотя должно считаться).
- Скрипт, требующий пакетов кроме numpy, scipy и PyWavelets (тетрадь может дополнительно использовать matplotlib и IPython, которые есть в любом Jupyter).
- `.npz`, который требует `allow_pickle=True`.
- Скрипт, непонятный студенту: функции на сотни строк там, где pywt делает то же одной строкой.

## Подходы

- **А. Один самодостаточный файл (выбран).** Вызовы pywt/scipy, где они дают те же числа; функции на numpy для остальных блоков вписываются в начало файла, только нужные; случайные отсчёты и неповторимые входы — из `.npz`; в конце сверка. Тот же текст выдаётся тетрадью. Цена: длинный файл у тяжёлых графов и второе воплощение 136 блоков на Python, которое надо держать в согласии с C++ — его держит тест каждого блока в CI.
- **Б. Короткий скрипт и модуль `signals_ref.py` рядом.** Верх читается лучше, но устройство блока спрятано в модуле, а передать работу — два файла. Хуже для учёбы.
- **В. Только библиотечные блоки, остальное из `.npz`.** Дёшево, но для половины блоков сверка ничего не проверяет и учиться по ним нечему.

## Устройство

### 1. Форматы `.npy` и `.npz`

- Свой читатель и писатель `.npy` (версии заголовка 1.0, 2.0 и 3.0, порядок байтов `<` и `>`, `fortran_order` true и false). Запись — `<f8`, а для строк — `<U`. Чтение — `f8`, `f4`, `i1`…`i8`, `u1`…`u8`, `b1`; комплексные и объектные массивы — отказ с понятной ошибкой. Всё переводится в `double`.
- `.npz` — ZIP-архив `.npy` файлов. Запись без сжатия (как `np.savez`); чтение — без сжатия и со сжатием deflate (`np.savez_compressed`). Для ZIP и deflate берётся библиотека с лицензией MIT или подобной (например, miniz) — GPL в ядре нельзя (`03-design.md` §2).
- Размер массива проверяется до выделения памяти: не больше `kMaxSamples` отсчётов на канал, как у других источников.

### 2. Как значения ложатся в файлы

Один файл `.npz` хранит одно значение; ключи ниже. Для `.npy` хранится только массив. В конвейере значения бывают трёх видов — сигнал, коэффициенты и отчёт: порты банка фильтров и числа объявлены, но ни один из 136 блоков их не использует.

| Тип порта | Ключи `.npz` | Замечания |
|---|---|---|
| сигнал | `x` — `(N,)` для одного канала, `(C, N)` для нескольких; `rate` | `.npy` — только `x`; `(C, N)`, как у librosa, чтобы pywt и scipy работали по последней оси |
| коэффициенты | как у pywt для данного преобразования (ниже); `wavelet`, `mode`, `rate`, `transform`, `length` (длина исходного сигнала), `detail_sign` | |
| отчёт | по ключу на поле: число — `f8`, строка — `<U`; `passed` | порядок полей — в `fields` (`<U`) |

Коэффициенты, по преобразованиям:

- `dwt`: `cA{J}`, `cD{J}` … `cD1` — так, что `pywt.waverec([f["cA3"], f["cD3"], f["cD2"], f["cD1"]], str(f["wavelet"]), mode=str(f["mode"]))` восстанавливает сигнал;
- `swt`: `cA{j}` и `cD{j}` для каждого уровня, порядок и `norm` как у `pywt.swt`;
- `wpt`: по ключу на лист базиса, имя пути узла как у `pywt.WaveletPacket` (`aad`, …);
- лифтинг (блоки `lift53` и `lift97`): те же ключи `cA{J}`, `cD{J}` … `cD1`; `transform` — `lift53`, `lift53i` (целый вариант, `integer = yes`) или `lift97`, остальные служебные ключи — из тех же полей коэффициентов, что у `dwt`. Аналога в pywt нет, поэтому обещание «файл сразу идёт в `pywt.waverec`» относится только к `dwt`, `swt` и `wpt`;
- `dtcwt`: действительная и мнимая части полос отдельными ключами (`re_…`, `im_…`).

Многоканальные коэффициенты — массивы `(C, len)`. Блок `mra` выдаёт сигнал (одну компоненту КМА во временной области), а не коэффициенты, и пишется как сигнал.

**Знак деталей.** Signals считает детали с обратным знаком относительно pywt (соглашение Стрэнга–Нгуена; закреплено тестом «default detail sign is the negated pywt sign»). Вне программы всё в знаке pywt:

- при записи коэффициентов `dwt`, `swt` и `wpt` знак каждой полосы приводится к знаку pywt (у `wpt` — по числу шагов `d` в пути узла), в файл пишется `detail_sign = "pywt"`;
- при чтении файл без ключа `detail_sign` или с `"pywt"` приводится обратно к знаку Signals; `"signals"` читается как есть; другое значение — ошибка;
- у лифтинга и `dtcwt` аналога в pywt нет: их полосы пишутся как есть, `detail_sign = "signals"`;
- в заголовке скрипта одна строка: детали здесь в знаке pywt, на экранах Signals они с обратным знаком; восстановленные сигналы от знака не зависят.

**Банк фильтров** не значение конвейера, но выгружается отдельно (§3): ключи `dec_lo`, `dec_hi`, `rec_lo`, `rec_hi` в точности как `pywt.Wavelet(...).filter_bank` (и в знаке pywt), плюс `name`. Тогда `pywt.Wavelet(str(f["name"]), filter_bank=[f[k] for k in ("dec_lo", "dec_hi", "rec_lo", "rec_hi")])` строит тот же вейвлет. Эти же ключи скрипт берёт из `.npz` данных, когда строит вейвлет по числам Signals (§5).

### 3. Выгрузка

- **CLI:** `signals run --npz out.npz` пишет все щупы в один `.npz` (ключ — имя щупа, затем `.` и ключ значения из таблицы выше); `--probe-dir` получает `--probe-format wav|json|npy`; `signals dwt -o out.npz` пишет коэффициенты в формате выше; `signals filter info <вейвлет> -o bank.npz` пишет банк фильтров.
- **Блоки:** `export` получает формат `npy`, `export_report` — формат `npz`.
- **Интерфейс:** щуп по `x` пишет `.npy` (или `.npz` для не-сигналов) по расширению пути; «Разложение» выгружает коэффициенты в `.npz` клавишей и пунктом палитры; «Фильтры» так же выгружают банк выбранного вейвлета; любой другой экран, где уже есть выгрузка значения в CSV, получает и `.npy`.

### 4. Загрузка

- Блок `wav` и открытие файла на вкладке «Сигнал» читают `.npy` и `.npz`, определяя формат по содержимому (`\x93NUMPY` и `PK\x03\x04`), как сейчас WAV, FLAC и MP3. Блок получает параметры `rate` (частота для `.npy`, где её нет; для `.npz` с ключом `rate` она берётся из файла, а противоречие с параметром — ошибка) и `key` (какой массив взять из `.npz`; по умолчанию `x`, а если ключ один — он).
- Массив `(N,)` — один канал; `(C, N)` — C каналов; другие формы — ошибка с формой в тексте.
- Новый блок-источник **`coeffs_file`** («Коэффициенты из файла») читает `.npz` коэффициентов и выдаёт их на порт коэффициентов. Ключи `wavelet` и `mode` обязательны; если их нет (файл записан вручную), их можно задать параметрами блока. Длины полос проверяются на согласие с вейвлетом и режимом, как у `idwt`.
- Диалог открытия файла показывает `.npy` и `.npz` рядом со звуком.

### 5. Генератор скрипта: `signals python`

`signals python graph.sig [-o out.py|out.ipynb] [--set узел.параметр=значение …]`. Без `-o` пишет `graph.py` рядом с графом. Файл данных — рядом с выходом, с тем же именем и расширением `.npz`. Перезапись — как у остальных команд выгрузки.

Порядок работы:

1. Граф проверяется и выполняется, как в `signals run`. Ошибка — тот же текст и код выхода, файлов нет.
2. Для каждого узла в порядке выполнения берётся Python-форма его блока (п. 6). Если у блока или выбранного значения параметра формы нет, выгрузка останавливается с именем узла, блока и параметра.
3. В `.npz` кладётся только то, что Python не может повторить сам: случайные отсчёты каждого блока с `seed` (шум `gen`, `add_noise`, сглаживание `wav_out` и т. п. — до масштабирования, чтобы формула масштаба осталась в скрипте), отсчёты входов, которые scipy не читает в те же числа (FLAC, MP3, µ-law и A-law WAV), длинные массивы параметров (больше 64 чисел), и значения всех щупов и отчётов для сверки.
4. Текст собирается так:
   - заголовок: из какого графа и какой версией Signals сделан, как запустить, версии numpy/scipy/pywt, на которых сверялся CI; строка о знаке деталей (§2), если в графе есть `dwt`, `swt` или `wpt`;
   - импорт `numpy`, `scipy.signal` и т. п., `pywt` — только нужные;
   - функции блоков без библиотечной формы, только нужные, каждая один раз;
   - загрузка `.npz` по пути рядом со скриптом (`Path(__file__).with_suffix(".npz")`; в тетради — относительно текущей папки);
   - по строке или короткому абзацу на узел, в порядке выполнения; переменная — имя узла (если оно совпадает с ключевым словом Python, встроенным именем или импортом, добавляется `_`); над узлом — строка `.sig` этого узла как комментарий;
   - параметры — уже вычисленные числа (`repr` даёт точное значение); если в `.sig` было выражение, оно стоит в комментарии;
   - побочные действия: `wav_out` пишет WAV через `scipy.io.wavfile` тем же форматом; `export` и `export_report` пишут файлы; `listen` в тетради — `IPython.display.Audio`, в скрипте — печать «послушать: …»;
   - вейвлет: по имени (`"db2"`), если фильтры pywt совпадают с фильтрами Signals до 10⁻¹⁵; иначе (сейчас — симлеты, которые Signals строит сам и которые расходятся с таблицей pywt до 10⁻¹⁰) — одна строка `w = pywt.Wavelet("sym8", filter_bank=…)` с числами Signals из `.npz` данных (ключи как у банка в §2) и комментарием, почему. Какие вейвлеты идут по имени, генератор берёт из таблицы в программе; тест моста сверяет эту таблицу с pywt;
   - сверка: функция `check` сравнивает каждый щуп и каждое поле отчёта с `.npz`, печатает таблицу «щуп — макс. |Python − Signals| — допуск — откуда допуск — ✓/✗» и выходит с кодом 1 при любом расхождении. Допуск: `max|a − b| ≤ tol · max(1, max|b|)`, `tol` — по §5.1; целые и строковые поля — точное равенство.
5. Комментарии и тексты в скрипте и тетради — на языке интерфейса (`--lang`), через словарь i18n.
6. Тетрадь `.ipynb` (nbformat 4): ячейка-заголовок; ячейка импорта; одна ячейка со всеми функциями блоков; по ячейке на узел — над ней markdown с названием и описанием блока из `explain`; после щупов — график matplotlib; последняя ячейка — сверка. Тетрадь сохраняется без выходов ячеек.

#### 5.1. Допуски

По умолчанию `tol` = 10⁻¹². Слабее — только у блоков из этой таблицы; это места, где библиотечный вызов даёт те же числа лишь до указанного порядка (по нынешним тестам против scipy и pywt), а пользователь выбрал читаемый вызов, а не перенос алгоритма Signals на numpy:

| Блок | `tol` | Чем вызывается в скрипте | Где измерено расхождение |
|---|---|---|---|
| `iir` (все семейства) | 10⁻⁸ | `scipy.signal.iirfilter(..., output="sos")`, `sosfilt` / `sosfiltfilt` | `tests/core/test_iir.cpp`: нули, полюса и усиление цифровых фильтров против scipy |
| `remez` | 10⁻⁸ | `scipy.signal.remez` | `tests/core/test_fir.cpp` |
| `firls` | 10⁻¹⁰ | `scipy.signal.firls` | `tests/core/test_fir.cpp` |
| `lms` (`rule` = `nlms` и `lms`) | 10⁻¹⁰ | своя функция | `tests/core/test_adaptive.cpp` (допуск M8a) |
| `sst_band`, `sst_ridge` | 10⁻¹⁰ | своя функция (без `ssqueezepy`) | `tests/core/test_sst.cpp`, против `ssqueezepy` |
| `cepstrum` | 10⁻⁹ | своя функция на `numpy.fft` | `tests/core/test_analysis.cpp` |

Это начальное заполнение: остальные тесты блоков против scipy держат запас 10⁻¹⁰ по привычке, а не из-за измеренного расхождения, поэтому в таблицу не входят — их решает тест моста (правило «Новая строка» ниже).

Правила:

- **Цепочка.** Щуп или отчёт получает самый слабый допуск среди всех блоков выше него по графу (включая свой). Таблица сверки печатает этот допуск и блок, который его задал.
- **Новая строка.** Если тест моста покажет, что блок с библиотечным вызовом не сходится до 10⁻¹², строитель добавляет его в эту таблицу с измеренной ошибкой, округлённой вверх до степени 10, и перечисляет добавленные строки в описании PR. Ослабить допуск где-то ещё (в коде теста, в скрипте) — анти-цель.
- **Своя функция** вместо библиотечной пишется, только если библиотечный вызов вообще не повторяет блок (другая формула, другая граница), а не ради лишних разрядов.

#### 5.2. Блоки с выбором

Пики, онсеты, основной тон, порог `sure`, лучший базис `wpt` и подобные выбирают по сравнению величин. Их Python-форма считает решающую величину теми же операциями и в том же порядке, что C++, и сравнивает тем же знаком (`<` или `<=`). В графах тестов нет точных равенств решающих величин; если у графа пользователя выбор на точном равенстве разойдётся, сверка честно показывает ✗ — это описано в документации пользователя. Выход программы ради этого не меняется.

#### 5.3. Знак деталей в формах блоков

Скрипт работает в знаке pywt (§2), эталоны щупов-коэффициентов в `.npz` данных — тоже. Блоки над коэффициентами, которые перестановочны со сменой знака деталей (`threshold`, `band_edit`, `keep_largest`, `coeff_quantize` с симметричным `round`, …), записываются как есть. Блок, который не перестановочен, в своей форме явно меняет знак до и после операции; поле отчёта, меняющее знак вместе с деталями, пишется в эталон в знаке pywt. Какие блоки такие, находит тест каждого блока.

### 6. Python-формы блоков

- У каждого блока есть Python-форма: шаблон строки (или абзаца) для узла, список нужных импортов и функций. Где форма зависит от параметра (например, `ext`, `rule`, `kind`), шаблон выбирается по значению.
- Функции на numpy лежат отдельными файлами в `resources/python/` и встраиваются в программу, как примеры `.sig`. Образец для большинства — `tools/gen_golden.py`, `tools/gen_dtcwt.py` и `tools/gen_sst.py`; но в сгенерированном скрипте нет `dtcwt`, `ssqueezepy`, `skimage` — то, что сейчас берётся из них, переписывается на numpy.
- Библиотечный вызов разрешён, если он повторяет блок в пределах 10⁻¹² или допуска из §5.1; иначе — своя функция. Решает тест блока, а не ожидание.
- Тест полноты: у каждого из 136 блоков (и у каждого блока, добавленного позже) есть форма для каждого значения каждого параметра-выбора; иначе тест падает с именем блока.
- `signals explain <блок>` и инспектор «Конвейера» показывают форму блока с параметрами по умолчанию («В Python: `pywt.wavedec(x, "db2", mode="symmetric")`»). Её же получает подсказка в VS Code через `data/blocks.*.json`.

### 7. `explain --json` (Н69)

`signals explain <блок> --json` выдаёт то же, что текстовый вид: порты, параметры с допустимыми значениями и их смыслом, карточку теории и Python-форму. `data/blocks.*.json` расширения VS Code строится из этого же вывода.

## Решения, принятые мной

1. Команда — `signals python`, тетрадь — тем же путём по расширению `.ipynb`.
2. Сигнал в `.npy`/`.npz` — `(N,)` или `(C, N)`, как у librosa: pywt и scipy работают по последней оси.
3. Ключи коэффициентов — как у pywt, чтобы файл сразу шёл в `pywt.waverec` и обратно.
4. Случайные отсчёты всегда из `.npz` — генератор C++ не воспроизводится в numpy; масштаб шума считается в скрипте.
5. WAV скрипт читает сам через `scipy.io.wavfile` (те же делители 128, 32768, 2²³, 2³¹, что в программе); FLAC, MP3, µ-law и A-law — из `.npz`.
6. Зависимости скрипта — только numpy, scipy, PyWavelets; `dtcwt`, `ssqueezepy`, `skimage` в скрипт не попадают.
7. Допуск сверки — относительно пика значения, `max(1, max|b|)`, чтобы громкий сигнал не проваливал 10⁻¹² из-за округления.
8. Комментарии скрипта — на языке интерфейса.
9. Загрузка банков фильтров из `.npz` не делается: для них есть `.flt`.
10. Python-форма блока показывается в `explain`, инспекторе и подсказке VS Code — так «под капотом» получает и вид на Python.
11. Выпуск 0.9.0 — последним PR этой стопки.
12. Банк фильтров и число убраны из таблицы значений конвейера: ни один блок не использует эти порты. Банк выгружается отдельно — `signals filter info <вейвлет> -o bank.npz` и экран «Фильтры», ключи как у `pywt.Wavelet(...).filter_bank`.
13. Лифтинг (`lift53`, в том числе целый `lift53i`, и `lift97`) пишется ключами `cA`/`cD` с `transform`; обещание `pywt.waverec` — только для `dwt`, `swt` и `wpt`. `mra` пишется как сигнал.
14. Допуск по цепочке: щуп получает самый слабый допуск среди блоков выше по графу; таблица сверки называет блок, который его задал. Обращения Гохберга–Семенцула нет среди блоков, из целей оно убрано; 10⁻¹⁰ из M8a остаётся у `lms`.
15. Таблица допусков §5.1 заполнена по нынешним тестам против библиотек; новая строка — только по измерению теста моста и с перечислением в описании PR.
16. Блоки с выбором считают решающую величину в том же порядке, что C++; точные равенства не гарантируются и описаны в документации, выход программы не меняется.
17. Вейвлет в скрипте — по имени, если фильтры pywt совпадают с фильтрами Signals до 10⁻¹⁵; иначе `filter_bank` из чисел Signals.
18. Знак pywt у `wpt` — по числу шагов `d` в пути узла; файлы без `detail_sign` считаются файлами pywt; блоки, не перестановочные со сменой знака, меняют знак в своей форме явно.
