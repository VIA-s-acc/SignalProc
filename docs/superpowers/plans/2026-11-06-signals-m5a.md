# Signals M5a: конвейер — граф, `.sig`, исполнитель, CLI — план реализации

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** любая обработка из [ядро] собирается в граф блоков, хранится в текстовом `.sig` и запускается из CLI с прогрессом, кэшем и щупами. `denoise.sig` даёт тот же результат, что `signals denoise`.

**Architecture:**
- **Слой `pipeline`** (`src/pipeline/`, библиотека `signals_pipeline`), §5 спеки. Зависит от `core`, `io` и Taskflow, про интерфейс не знает.
  - Значения на проводах: сигнал, коэффициенты, фильтр, число, отчёт.
  - Типы блоков — реестр с параметрами, портами и функцией запуска поверх уже готовых функций `core` и `io`.
  - Формат `.sig`: разбор, запись, подстановки `--set`.
  - Граф: проверка типов, циклов и обязательных входов, порядок запуска.
  - Исполнитель на Taskflow: этапы с прогрессом, отмена, время и память по узлам, кэш результатов, щупы.
- **CLI:** `signals run` и `signals graph`.
- **TUI** — редактор, щупы и A/B — следующий план M5b. В M5a интерфейс не меняется, кроме того, что `JobRunner` умеет показывать этапы конвейера, если план до этого дойдёт.

**Tech Stack:** как в M4, плюс Taskflow v4.1.0 (§4 спеки, через `FetchContent`).

**Spec:** `docs/03-design.md`:
- §5 — слой `pipeline`;
- §7.3 — блоки [ядро];
- §8.4 — этапы и прогресс;
- §8.8 — ресурсы по узлам;
- §9 — формат `.sig` и CLI;
- §13, строка M5.

**Границы M5a и решения (моё решение — пользователь может оспорить).**
1. **Типы портов:** `signal` (многоканальный `AudioBuffer`), `coeffs` (коэффициенты DWT по каналам вместе с банком и режимом краёв), `filter` (банк), `scalar`, `report` (поля «имя → число или текст»). Несовместимое соединение — ошибка с подсказкой.
2. **Блоки M5a — все [ядро] из §7.3**, кроме прослушивания: оно живёт в TUI (M5b), в CLI блок `listen` пропускается с предупреждением. Имена типов совпадают с id карточек `theory::block_catalog()`, поэтому `F1` на узле в M5b откроет его карточку без таблицы соответствий.
3. **Грамматика `.sig`** — по образцу §9:
   - `pipeline "имя" v1`;
   - `node id = тип(ключ=значение, …)`;
   - цепочки `a -> b -> c` и порты `узел.порт`;
   - `probe узел.порт as "имя"`;
   - комментарии `#`.
   Значения: числа, идентификаторы, строки в кавычках, диапазоны `1..4`. Позиции узлов не хранятся (§9).
4. **Порты по умолчанию:** у блока с одним входом и одним выходом порт в цепочке можно не писать. Именованные порты нужны там, где их несколько (`chk.ref`, `chk.in`, `dwt.d3`).
5. **Относительные пути** в `.sig` считаются от каталога самого файла, а не от текущего каталога.
6. **Кэш** — по ключу «тип блока, параметры, ключи входов». Повторный запуск с `--set` на одном узле пересчитывает только этот узел и его потомков. Бюджет памяти кэша — четверть физической памяти; при превышении вытесняются самые старые результаты.
7. **Щуп** — именованная копия значения на проводе. CLI пишет щупы в `--json` (сводка: длина, энергия, пик) и, по флагу `--probe-dir`, в файлы: WAV для сигнала, JSON для коэффициентов.
8. **`signals graph`** — текстовая раскладка Сугиямы: слои по самому длинному пути, порядок внутри слоя по барицентрам (4 прохода), провода — `│ ─ ┼ ▼`. В ASCII-режиме — `| - + v`.
9. **Отмена:** `Ctrl+C` в CLI прерывает запуск между блоками и внутри долгих блоков через `ProgressSink`. Частичный результат не пишется.

Все пути — от корня репозитория. Работа идёт в ветке `m5a-pipeline` от `main` после слияния M4b.

## Global Constraints

- Все ограничения M4b.
- `signals_pipeline` не зависит от `signals_tui`, FTXUI, `audio` и `theory`.
- Ошибки — `core::Result` с позицией (строка, колонка) для `.sig`; тексты для человека — через словарь `ru.json`, код и сообщения разработчику — на английском.
- Блок не дублирует математику: каждый тип блока вызывает готовую функцию `core` или `io`. Новая математика, если понадобится, — в `core` с тестом.
- Детерминизм: один и тот же `.sig` с теми же входами даёт побайтно один и тот же выход. Dither — с фиксированным зерном из параметров блока.
- Снимочные тесты — нет (нет нового интерфейса). Тесты CLI — через `run_cli` в процессе.

## Review Focus

1. **Неправильный граф:** цикл, порт неверного типа, не подключённый обязательный вход, неизвестный блок или параметр, два провода в один вход. Ожидается понятная ошибка с номером строки `.sig` и без запуска чего-либо. Тест в Task 3 и 4.
2. **`--set` на несуществующий узел или параметр, значение не того типа** — ошибка до запуска, с подсказкой ближайшего имени. Тест в Task 3.
3. **Отмена посреди долгого блока** (DWT 10 минут стерео): запуск останавливается быстро, файл не пишется, временных файлов не остаётся. Тест в Task 5.
4. **Кэш:** смена одного параметра пересчитывает ровно один узел и его потомков; результат не меняется от того, был ли кэш. Тест в Task 5.
5. **Пути:** относительный путь в `.sig` из другого каталога, пробелы и кириллица в путях. Тест в Task 3 и 6.

```cpp
enum class PortType { signal, coeffs, filter, scalar, report };
struct Coeffs { std::vector<core::BasicCoeffs<double>> channels; std::string wavelet; core::Extension mode; double rate = 0; };
struct Report { std::vector<std::pair<std::string, std::variant<double, std::string>>> fields; };
using Value = std::variant<core::AudioBuffer, Coeffs, core::FilterBank, double, Report>;
PortType type_of(const Value& v);
std::uint64_t value_key(const Value& v);                 // stable content hash for the cache

struct ParamSpec { std::string name; enum class Kind { integer, real, text, choice, path, range } kind; std::string fallback; std::vector<std::string> choices; };
struct PortSpec { std::string name; PortType type; bool optional = false; };

const BlockType* find_block_type(std::string_view id);
std::span<const BlockType> block_types();
core::Result<Params> resolve_params(const BlockType& t, const Params& given);   // defaults, choices, ranges
```

- Produces:

```cpp
enum class NodeState { waiting, running, done, failed, bypassed, cached };
struct NodeStatus { std::string id; NodeState state = NodeState::waiting; double fraction = 0, cpu_seconds = 0, wall_seconds = 0; std::size_t bytes = 0; std::string message; };
struct RunEvents { std::function<void(const NodeStatus&)> on_node; };   // called from worker threads
```
